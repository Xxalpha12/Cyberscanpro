🔬Theory — Technology Acceptance Model (TAM)
LIKELY Q1▼

What is TAM?

The Technology Acceptance Model (TAM), developed by Fred Davis in 1989, explains why people accept and use technology. It has two core constructs:

1.Perceived Usefulness (PU) — the degree to which a user believes the system improves their performance. For CyberScan Pro: does it find vulnerabilities faster and better than alternatives?
2.Perceived Ease of Use (PEOU) — the degree to which a user believes the system is free of effort. For CyberScan Pro: is the dashboard intuitive without needing command-line expertise?
// TAM FLOW
External Variables → PU (Perceived Usefulness) → Behavioural Intention → Actual Use ↘ PEOU (Perceived Ease of Use) ↗ ↑ └──────────────────────────────┘
Defense answer: "I used the Technology Acceptance Model by Davis (1989) because CyberScan Pro's success depends on actual adoption. TAM's two constructs — PU and PEOU — directly map to whether users find the tool effective and easy enough to use over existing alternatives."

Why NOT UTAUT or Waterfall?

UTAUT adds social influence and facilitating conditions — better for large organisational rollouts. TAM is simpler and sufficient for evaluating a single-user security tool. Waterfall is a development model, not a theoretical framework — it does not explain user adoption.

TAM vs Agile — they are NOT the same thing

TAM = theoretical framework for evaluating user acceptance → Chapter 2
Agile = development methodology for building the system → Chapter 3

📖Empirical Review — What Others Wrote About Your Topic
LIKELY Q2▼

What is an Empirical Review?

An empirical review presents findings from actual studies, experiments, and surveys — NOT theories. It shows what researchers tested and concluded. Yours is in Chapter 2, Section 2.4 (10 studies from 2015–2020).

Key Studies to Know

1.OWASP Foundation (2021) — SQL Injection, XSS, and Broken Authentication are the top 3 web vulnerabilities, in over 60% of web applications tested.
2.Verizon DBIR (2019) — 80% of data breaches exploited vulnerabilities that had patches available at the time.
3.Gordon et al. (2018) — Organisations with regular vulnerability assessment had 47% fewer successful cyberattacks.
4.Peltier (2018) — Reports with plain-English explanations achieved 63% higher remediation completion than raw technical output.
5.Abubakar et al. (2021) — 87% of Nigerian university websites had at least one High severity vulnerability; 63% had never been assessed.
6.Kim & Solomon (2020) — Commercial tools cost ~USD 3,000/year — prohibitive for small organisations. Open-source tools with integrated scanning are the only viable option.
🔭Research Design, Population, Sampling, Data Collection
LIKELY Q3–Q7▼

Research Design

Design and Development Research (DDR) — also called Design Science Research. Used because the primary output is a working software artefact. It has two activities: Building (creating CyberScan Pro) and Evaluating (testing it against targets and surveying users). Reference: Hevner et al. (2004).

Development Methodology

Agile Software Development (Beck et al., 2001). Organised into 9 sprints: infrastructure → network scanner → web tester → CVE engine → report generator → API enrichment → dashboard redesign → security hardening → testing & deployment.

// RESEARCH FLOW
Problem Statement ↓ Literature Review (Ch.2) → Theoretical Framework (TAM) ↓ System Design (Architecture, DB Schema) ↓ System Development (Agile — 9 Sprints) ↓ System Testing (scanme.nmap.org, testphp.vulnweb.com, FUPRE) ↓ User Evaluation (Questionnaire — 30 participants) ↓ Results Analysis (Quantitative + Qualitative) ↓ Conclusions & Recommendations

Population of Study

IT security professionals, system administrators, network engineers, and cybersecurity students within Nigerian tertiary institutions and SMEs. Technical population: FUPRE's web systems and authorised test targets.

Sampling Technique

Purposive (Judgement) Sampling — deliberately selecting participants based on their relevance to the research: at least 1 year experience in IT/security role, and test targets with documented scanning authorisation. Used instead of random sampling because random selection would not guarantee the expertise or system characteristics needed.

Sample Size

30 participants: 15 IT administrators, 10 final-year CS students, 5 external cybersecurity practitioners.

Questionnaire

Structured Likert-scale questionnaire (5-point: 1=Strongly Disagree to 5=Strongly Agree). Three sections: demographics, 10 PU items, 10 PEOU items. Aligned with Davis (1989) TAM instrument. Distributed via physical copies at FUPRE and Google Forms digitally. Respondents given a live demo before answering.

Data Analysis

Quantitative: frequency distribution, mean scores, detection accuracy %, false positive rate. Qualitative: thematic analysis of open-ended responses (Braun & Clarke, 2006). Triangulation: both methods cross-referenced for comprehensive conclusions.

⚠️Statement of Problem & Research Gap
LIKELY Q8–Q9▼

Statement of Problem

Despite growing cybersecurity threats, many Nigerian institutions and SMEs lack access to affordable, automated vulnerability assessment tools. Commercial tools like Nessus cost USD 3,000+/year. Open-source alternatives require command-line expertise. No existing tool combines network scanning, web application testing, and CVE intelligence in one accessible platform with professional reporting. This results in organisations remaining exposed to known, preventable vulnerabilities.

One sentence version: "The lack of an affordable, accessible, integrated web-based vulnerability assessment platform with professional reporting capabilities represents a critical gap in cybersecurity tooling available to Nigerian institutions."

Research Gap (3 maximum)

1.Integration gap — No open-source tool combines network scanning, web testing, and live CVE mapping in one interface (Bace & Mell, 2016; Weidman, 2018).
2.Accessibility gap — Existing tools require command-line proficiency, excluding non-specialist users (Kim & Solomon, 2020; Cybereason, 2022).
3.Reporting inadequacy — Tools produce XML/JSON output unsuitable for management reporting; plain-English reports produce 63% better remediation (Peltier, 2018).
